### 🟣⋯ The exemption has to speak
Both of the above may be skipped for a genuine throwaway one-off. **Say so before your first edit, or you have not taken the exemption — you have skipped the rule.**
> Treating this as a one-off, so no dimensions pass: `<why>`.

The trigger is **your first edit to a source file**, not your read of whether the request is "a feature". That distinction is the whole point.
e.g. *"lower the contrast of the background color of workspaces"* was classified as a one-off and built, tested and handed back before `conduct-product-dimensions` was invoked. It was a feature: it earned a ship-plan entry, a design finding that redirected the next change, and it exposed a latent renderer-drift defect in the code it touched. Nothing about the opening request looked like that.

So the rule cannot key on the request. An agent that has already decided "this is small" will not recognise itself in *"when starting a new feature."* It will recognise itself in *"I am about to edit a file and I have not said which mode I am in."* One visible sentence costs nothing when the call is right, and when it is wrong it surfaces in the second message instead of the eighth.

**Refuse this rationalization:** *"I'll do the pass afterwards if it turns out to matter."* → It did turn out to matter here, and the pass then ran on an existing implementation, which ratifies rather than verifies. A gate downstream of the thing it gates is not a gate.

### 🟣⋯ Build, run and test: `make`
The front door, so you never invent a **build-id** or hunt a DerivedData path.

**Where the build-id comes from: your jj bookmark first, then a git branch.** `tom-rigelblu/cm-19` → `cm-19`. jj keeps git's HEAD detached permanently, so in this checkout `git branch --show-current` is *empty* — the jj lookup is the one that fires, and the git path only matters in the git worktrees used for isolated builds. If neither resolves you get `detached-<sha>` **and a warning on stderr**, because that mints a fresh ~6GB DerivedData dir per commit. Git's `HEAD` follows jj's working copy, so it's often someone's undescribed work in progress, not a release. When you make a checkout or worktree, name the release commit; the tell is `git log --oneline -1 <sha>` printing a sha with no subject. The jj lookup is `heads(::@ & bookmarks())`, skipping `zz-` bookmarks: the nearest bookmarked ancestor wins, so a probe change on a release builds into the release's slot, and of several bookmarks on one commit the alphabetically first wins. When a bookmark you didn't set lands on your commit, say so and pass `BUILD_ID=<yours>`.

The build-id is what `scripts/reload.sh --tag` takes. It decides the DerivedData dir, the debug socket, the app name, and the bundle id suffix — so two dev builds never collide. It is a *component* of the bundle id, not a peer: build-id `cm-18` gives `com.cmuxterm.app.debug.cm.18` (reload.sh maps non-alnum runs to dots, so the hyphen does not survive). That is why changing it resets TCC grants and keychain-backed sign-in — the same mechanism behind `#cm-17`'s "sign-in does not migrate".

```bash
make run                       # build this branch's build-id and launch it
make build                     # build only; prints the App path
make test                      # cmux-unit, then cmux-cli-tests — nothing else compiles the unit tests
make test-packages             # swift test for every package in rbf-package-tests.sh's list; not the app
make clean-builds              # reclaim ~6GB per build-id; keeps running/most-recent/current, no branch check (-plan previews)
make install-rbf               # build + install `cmux RBF.app` (install-rbf-plan previews)
make run BUILD_ID=spike        # a second build alongside your branch's
make build ARGS=--prod-auth    # extra flags → reload.sh (for `make test`, → xcodebuild)
make help
```

Logic lives in `rbf/scripts/dev.sh`, except what `make install-rbf` also needs — that lives in `rbf/scripts/lib/`, because `make install-rbf` calls `rbf/scripts/install-rbf.sh` directly and never passes through `dev.sh`.

**`make test` runs two schemes, `cmux-unit` then `cmux-cli-tests`** (`#cm-142.1`). The sync moved upstream's CLI test classes into a second target, `cmuxCLITests`, and only `cmux-cli-tests` runs it. The `ARGS` rules (`rbf/scripts/dev.sh`, the `test)` branch):
- `ARGS` naming only `-only-testing:cmuxCLITests/…` runs the CLI scheme alone; naming only `-only-testing:cmuxTests/…` runs the unit scheme alone
- with both kinds, each scheme gets only its own `-only-testing` filters, because `xcodebuild` refuses a filter that names a target outside the scheme. Every other argument goes to both
- each scheme writes its own result bundle, `cmux-<id>.xcresult` and `cmux-<id>-cli.xcresult`. The exit status is the first failing scheme's, so read both bundles before calling a run green

### 🟣⋯ How to hand a build back
**Give Tom the command, not the path.** When a change is ready to look at, end with the `make` line he should run:

```
Ready to look at:  make run
```

Name a non-default build-id only when the work genuinely needs one (`make run BUILD_ID=spike`), and say why in the same breath.

**Never hand back a `file://` link to a `.app`** — that is upstream's convention and it is pruned from `CLAUDE.md`. A path addresses a bundle *that was already built*, so it keeps resolving after the tree moves on and launches the previous build without saying so. Observed 2026-08-02 on `#cm-20`: a link offered as the fix pointed at the prior value of the constant, because the intervening command was `make test`, which builds `cmux-unit` and never touches the app. `make run` rebuilds, so it cannot be stale; a link cannot know whether it is.

The same holds for pasting a DerivedData path as prose, and `BUILD_ID` takes a **build-id**, never a filename — `BUILD_ID=cm-17.app` mints `cmux DEV cm-17.app.app` with its own ~6GB DerivedData dir and its own bundle id, which resets TCC grants and keychain sign-in.

#### 🟡⋯ If you did not build in Tom's checkout, say where you built
Bare `make run` means *"whatever your current directory's branch resolves to"*. Run in Tom's tree it builds **Tom's** branch, not yours — so an agent working in its own worktree that hands back bare `make run` is handing back someone else's build. Give the directory:

```
Ready to look at:  make -C /Volumes/Tom's HDD/tmp/<your-worktree> run
```

Absolute path, always. `make -C` moves make's working directory before anything runs, and the derivation is **cwd-relative** (`derive_build_id()` tests `.jj` and `git branch --show-current` in `$PWD`), so `-C` is what makes it read *your* branch.

**Do not reach for `BUILD_ID` to do this.** The build-id names the *output slot*; the checkout names the *source*. `make run BUILD_ID=<yours>` in Tom's tree compiles **his** working copy into a slot wearing **your** name — wrong code, right-looking app, no error. That is strictly worse than a stale link, which at least shows an app someone really built.

`BUILD_ID` has exactly one use in a multi-agent session: **two agents on the same branch name**. Distinct branches already isolate everything — build-id, DerivedData, debug socket, bundle id — with no flag at all. Same branch in two worktrees collides on all four, and one of the two must pass `BUILD_ID=<something>` and say so.

Before handing back, confirm the tree you built is the tree you are naming: `make -C <path> help` prints `current build-id:` and costs nothing.

The first two were each first patched at whichever entrypoint surfaced it, and each then failed again at the next one — XcodeProj at `build`, then `test`, then `install`; Zig at `build`/`run`, then `install`. **A guard written inside one entrypoint cannot be inherited by a second; only a copy can, and nobody copies what they don't know exists.** Put new ones in `Package.swift` or `rbf/scripts/lib/`.

**`make install-rbf` builds into `$TMPDIR`, and macOS prunes `$TMPDIR` nightly — a partial fix cannot work, only a full wipe.** `install-rbf.sh:265` puts DerivedData at `$(rbf_tmp_dir cmux-rbf-cm-17-install)/derived`, i.e. under `/var/folders/…/T/`, which the system cleans by **access time** around 03:35. It takes whatever the last build didn't touch and leaves everything else, so what you get back is a tree xcodebuild still believes in.

Measured 2026-09-17 on `#cm-96.3`'s v0.27.5 install — three failures, three different symptoms, one cause:

1. `Info.plist` missing from the Sparkle, Sentry and Iroh xcframeworks. Removing `SourcePackages/artifacts` was not enough.
2. `There is no XCFramework found` — `workspace-state.json` still recorded the artifacts as resolved, so `-resolvePackageDependencies` trusted its own record. Removing all of `SourcePackages` and re-resolving fixed that leg, and the build then failed on the next one.
3. `module 'GhosttyKit' not found` — the Headers directory beside `Build/Products/Release/libghostty-internal.a` had been pruned while the `.a` survived.

**Delete the whole DerivedData directory and re-run.** It is ~10 GB and about 25 minutes, which is cheaper than the third guess. The tell that you are in this and not in a real build break: the failure names a dependency nobody touched, and `jj diff` shows nothing near it.

**Quit any running tagged app before `make test`**, or the run dies with "Test runner never began executing tests", exit 65, zero tests run.

**A test that runs a resume command through `zsh` must never read your real `$HOME`** — fixed in `#cm-58` for the one test that did. `testAgentHookSurfaceResumeStartupInputRunsWhenSavedWorkingDirectoryWasDeleted` put a fake `codex` first on `PATH`, but ran a login shell with the host's environment, and a binding with `environment` makes `startupInput` nest a second `/bin/zsh -lc`. Either login shell reads `~/.zprofile`, which can put a real `codex` ahead of the fake, so the test started an interactive `codex resume session-duplicate-turn -c check_for_update_on_startup=false --yolo` and waited on it forever — the stray process that stalled `make test` at 0% CPU in at least `#cm-56`, `#cm-54`, `#cm-69.1` and `#cm-75` sessions. **Copy the fixed shape** for any new test that executes one: outer `zsh -fc`; an environment of only a sandbox `HOME`, a minimal `PATH` and the test's own variables; a `.zprofile` in that `HOME` that puts the fake's dir first again (`path=('<bin>' $path)`, with any `'` in the path written `'\''` — an unmatched quote makes zsh skip the file silently), because every login shell runs `/etc/zprofile`'s `path_helper`, which moves `/usr/local/bin`, `/opt/homebrew/bin` and the rest ahead of whatever `PATH` it was given; and a bounded wait like the file-scope `runWithBoundedWait` in `cmuxTests/SessionPersistenceTests.swift`, which throws within 32 s (30 s, terminate, 2 s grace) and says whether the process was still running. That helper is `private` to its file, so a test in another file copies it too — two other copies already exist (`SessionPersistenceResumeBindingTests.swift`, and `ClaudeWrapperResumeEnvironmentTests.swift`, which the `cm-142` sync moved to `cmuxCLITests/`). **Measured 2026-09-14:** dropping only `HOME` brings the real `codex` back and the test fails at 30 s instead of hanging. **Still possible:** `#cm-35`'s unrelated stall in `AppDelegateShortcutRoutingTests`, so a hang is not automatically this one. Diagnose with `pgrep -fl '^codex resume session-duplicate-turn'` — anchor the pattern, since an unanchored one also matches any shell whose command line contains it, including the one you typed it in. A real hit's parent is the tagged test-host app, or `PPID 1` for an orphan from an interrupted run; kill that pid.

**More traps a build or test run hits here** — each one cost a session before it was written down:
- **`make build` and `make run` quit the running app of the same build-id.** Gate on it in the same command, `pgrep -f 'cmux DEV <id>' && { echo STOP; exit 1; }`, then ask Tom: `reload.sh` once quit his `cmux DEV cm-73` with a Claude session inside. It runs the other way too: his own `make run` mid-build kills both builds (`database is locked`), so tell him the app relaunches by itself, and check `ps` for a login-shell `make run` before diagnosing a failure. A compile-only check can use `xcodebuild` with its own `-derivedDataPath`, which never touches the app
- **Check `ps` before any `pkill`, and never match `cmux RBF`**, Tom's everyday app. A too-broad pattern killed two apps that weren't blocking anything
- **`make test` goes silent for two reasons:** `xcodebuild` wedged at 0% CPU, or `dev.sh` refusing because a killed run left its unit-test host alive (the refusal never says `error:`). The Xcode build also waits on any cargo on the machine, since `~/.cargo/.package-cache-mutate` is machine-global: find the holder with `lsof -p <cargo-pid> | grep cargo`, and don't kill it — it's someone's live work
- **A test run prints two result streams.** Swift Testing prints the function name, never the suite; read `Test run with N tests`. For a Swift Testing `@Suite`, XCTest's `Executed 0 tests` is the healthy result. A failure prints `􀢄  Test name() failed`, not `✘`, and `swift test --filter` takes the type name. Anchor log patterns to the line shape (`^/.*\.swift:[0-9]+:[0-9]+: error:`, `\*\* (BUILD|TEST) (SUCCEEDED|FAILED) \*\*`): a bare `error:` matched source text echoed into a passing log
- **`make test`'s tail is app logs.** Get failures from the `.xcresult` printed above `** TEST FAILED **`: `xcrun xcresulttool get test-results tests --path <path> --format json`. After "Restarting after unexpected exit", the tests that were running get no result, and the summary still counts only the rest — 14 crashed tests hid that way on `#cm-110.1`
- **`#expect(Double == CGFloat)` fails even on identical values** (Swift 6.4, measured 2026-10-26). Convert one side with `Double(...)` first. Neither `XCTWaiter().wait` nor a nested `RunLoop.main.run(until:)` drains the main dispatch queue, so a test awaiting a timer-delivered result fails every time
- **A fresh build-id resolves every feature flag to its `defaultWhenUnavailable`** until the remote config arrives. `strings` on `Contents/MacOS/<name>` proves nothing in a Debug build (the code is in `<name>.debug.dylib`), and `open --env VAR=1 <app>` exits 0 even when it drops the variable — exec the binary instead
- **A `Sources/*.swift` file needs pbxproj wiring too**, not only `cmuxTests/`: an unwired one compiles nowhere while every test passes. Check its reference with `rg -n "path = <Dir>;" -B3 cmux.xcodeproj/project.pbxproj`

Insert a key as text beside a neighbour, then validate with `json.load`. Check duplicates with `object_pairs_hook`, which plain `json.load` hides: it counts 0 at every level on `ee0dc596698f` (6,903 keys), the pin `3167a90f59ad` (8,676) and the `cm-142` merge (9,012), measured 2026-11-23. An older note here said 129; it no longer reproduces

### 🟣⋯ `/Applications` holds **two** cmux apps — check which one you are in
Since v0.9.0 (`#cm-17`) the flavour installs beside upstream rather than replacing it:

| App                          | Bundle id              | What it is                                           |
| ---                          | ---                    | ---                                                  |
| `/Applications/cmux RBF.app` | `com.cmuxterm.app.rbf` | **ours** — `make install-rbf` builds and installs it |
| `/Applications/cmux.app`     | `com.cmuxterm.app`     | upstream's, never read or written by the installer   |

**`env \| grep CMUX_BUNDLE_ID` is how a session tells which one hosts it**, and this matters beyond documentation. `#cm-17`'s opening measurement was exactly this reading — it found that every fork feature shipped to date was running in *upstream's* app, which is the finding that motivated the whole slice. An agent that assumes `/Applications/cmux.app` is the fork will draw wrong conclusions from a running app, and they will look like product bugs.

Do not read About to answer this. It reports `0.64.20 / 100` in **both** apps — the fork inherited both version keys at the fork point — until `#cm-17.3` lands in v0.10.0.

Two more consequences worth knowing before debugging something odd:

- `~/.config/cmux/cmux.json` resolves from `$HOME`, **not** the bundle id, so both apps share it. A settings change in one appears in the other; that is the design, not a leak.
- Everything else is bundle-id scoped — workspaces, window layout, session order, reopen history, and keychain auth. A separate bundle starts signed out **by construction**, and no file copy fixes it.

### 🟣⋯ The install can keep the app it replaces, and one command goes back (`#cm-142.2`)
Three fork-owned pieces, none of them upstream's. Their tests are scripts, and **`make test` runs none of them**: run each by hand, under `bash` and `/bin/bash`, after any change here.

# 🔵🏗️ Testing — keep the proof, drop the ceremony
- cmux-rbf does **not** use the two-commit red/green structure in `CLAUDE.md`. **Commit once.**

That red/green policy exists to show upstream's maintainers a red check turning green in the GitHub PR Commits tab. With no CI here (above), both commits would sit grey forever, so the structure proves nothing to anyone. It also forces stub commits whenever the test covers a type that doesn't exist yet.

What survives is the part that carries the evidence:
- Run each new behaviour test against the **unfixed** code first
- Confirm it fails *for the intended reason* — not a compile error, not a typo, not an unwired target
- Record the observed failure — the assertion message or the actual value — in the commit body or the feature brief
- Then implement, and commit **once**

A test never observed failing proves nothing, and this repo ships several ways to be fooled:
- An unwired `cmuxTests/` file reports `Executed 0 tests` and still passes review
- `./scripts/lint-pbxproj-test-wiring.sh` catches it, **but only when you run it yourself**; upstream's PR job does not fire here
- The `cmux` scheme compiles no unit tests and still prints `TEST BUILD SUCCEEDED` — use `cmux-unit`
- `-only-testing:` names a **class**, not a file; an unmatched filter runs nothing and still reports `TEST SUCCEEDED`
- A test guarding a production gate that has no consumer stays green no matter what the fix does

Whether a test proves anything at all — reds, mutations, fixtures, reaching the real code — is in the `verify-changes-yourself` skill's `references/proving-a-test.md`. Read it before you trust one.

### 🟣⋯ When you already wrote the test and the code together
It happens, especially for a new pure type where the test cannot compile until the type exists. The recovery is **mutation testing**, not a shrug: deliberately break the implementation one behaviour at a time and confirm the matching test fails.

A mutation nothing catches is the finding. Either the test does not discriminate, or the code is redundant because something downstream already compensates — both are worth knowing, and neither is visible from a green run. Restore from a backup copy afterwards, never by hand.
